# Pro offer testing and SKU scanning

This English fork translates the v7.6.0 documentation and report without changing the original subscription mapping. See the [README](../README.md) for the source mapping, installation, report, privacy and troubleshooting details. The report is a record of script execution, not evidence of eligibility or a successful purchase.

## 1. Module and compatibility

The English fork uses the main branch for its script references. The upstream v7.6.0 tag remains unchanged. Only one main module should be enabled; historical standalone scanning and test modules are compatibility entries. Existing data and schema versions are retained. The report version is distinct from the stored collector version.

## 2. HTTPS and data scope

The original module operates on the Google One hostname and uses a local Shadowrocket report. HTTPS decryption is a sensitive permission: only trust a certificate you control. The global UDP 443 rule can affect HTTP/3 connectivity in other apps. The scripts store only candidate IDs, counts, timestamps, status and sanitized route categories, not request bodies, headers, complete URLs or complete response bodies. No network reporting is implemented in the source.

## 3. Passive collection

The collector reads original text responses, excludes its own local report, and recognizes product-ID strings. It counts occurrences and deduplicates the list, retaining up to 300 distinct IDs. Existing IDs continue updating at capacity. Escape sequences representing dots are normalized in the discovery copy only. No active full-catalog lookup takes place. An ID in a response is not proof that a product is offered to the current account.

The latest ten response events are saved in chronological order in JSON and displayed newest first in HTML. An unchanged list can mean duplicate IDs, not necessarily a broken collector. Non-text responses have a separate counter. Compare actual saved collector version, counts, and event timestamps rather than assuming the report version identifies the collector.

## 4. Offer mapping and execution records

See the README's three-tier mapping table for the original source behavior and version history. The mapping acts on text, not native StoreKit or a verified App Store catalog. The displayed purchase sheet and actual account entitlement are authoritative. Candidate labels and historical screenshots are not verified prices, billing intervals or benefits. Do not assume a rewritten ID establishes eligibility.

The report preserves the most recent execution, not cumulative test history. Subsequent unmatched responses can replace that record. The configured candidate is separate from the saved target and version. Each matched row stores its complete source ID, actual target, count and fallback flag. Historical targets and origins remain unchanged.

## 5. Local report and JSON fields

The report includes the actual collector version, recent response history, latest execution and deduplicated IDs. The JSON export uses the same data. Both local storage keys and schemaVersion 1 are preserved.

| Field | Meaning |
|---|---|
| reportVersion | Report script version |
| configuredTarget | Current configured candidate |
| scan.version | Version of the saved collector |
| scan.scannedResponses | Cumulative text responses |
| scan.matchedResponses | Text responses with at least one candidate |
| scan.nonTextResponses | Non-text responses |
| scan.skus | ID, occurrence count and last-seen time |
| scan.recentResponses | Up to ten sanitized response events |
| test.version | Saved execution version |
| test.target | Saved 2TB target |
| test.targetOrigin | Saved origin: user-specified, pattern-derived, legacy, or empty |
| test.matchedFrom | Rows with id, to, count, fallback |
| test.hitCount | Total replacements |
| test.annualHitCount | 2TB replacements (legacy field name) |
| test.updatedAt | Execution timestamp, UTC |
| test.status | rewritten, no-match or non-text |

Each response event contains at (UTC), path (sanitized category), bodyType, status, candidateCount, addedCount and omittedCount. Counts in an event represent distinct IDs, unlike cumulative occurrence counts. Status new-skus takes priority when addedCount is positive. known-skus indicates previously stored IDs; no-skus indicates no recognized IDs; limit-reached indicates omissions with no new retained ID; non-text indicates a non-text body.

The report does not fabricate activity when older stored data lacks recentResponses. Manual clearing resets only the two tool-specific keys; export records before resetting.

## 6. SKU collection and validation on iOS

Passive collection records strings present in the response, including strings not rendered on the page. Strings never sent by the server cannot appear in that collection. A replacement generated by the script does not automatically become an observed candidate. Native StoreKit product lookup and actual purchase eligibility are separate from this report.

## 7. Troubleshooting

| Observation | Interpretation |
|---|---|
| No records or current-version responses | No current collector activity has been saved |
| Legacy collection records | Report updated; saved collector data may be older |
| No response history | Older data lacks this field; history is not reconstructed |
| Normal Google page or 404 | Local report is not being served |
| Storage unavailable or saved=no | A write/read failure may preserve old counts |
| Counts increase with known-skus | Duplicate data received |
| Counts increase with no-skus | No recognizable ID in the text response |
| Non-text count increases | Response not scannable as text |
| new-skus | Newly retained IDs |
| limit-reached | New IDs omitted at capacity |
| rewritten with zero 2TB hits | Other tiers matched; not a 2TB hit |
| no-match | No configured source matched that response |
| Identical target but old version | Still a historical execution |
| Purchase sheet differs from report | The actual store response is authoritative |

Check actual collector version and saved timestamps before interpreting the report. Reinstallation or clearing history cannot force the server to provide new IDs.

## 8. Device record template

Record test time and timezone; iOS, Google app and Shadowrocket versions; module and report versions; actual saved collector version; before/after response counts; latest sanitized event and status; candidate, added and omitted counts; original observed IDs; execution version, time, matched rows, configured and saved targets, target origin, total and 2TB replacement counts; actual App Store product, billing period, currency, initial price, renewal price and error message if present; actual entitlement only if legitimately purchased; and JSON export filename.

The source screenshots remain in their original language. Upstream credits and version history are retained in the README.
